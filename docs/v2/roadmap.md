# V2 阶段路线图

本路线图按用户结果推进，不按“两周”“第几天”或代码数量推进。AI 可以加快实现速度，但不能替代真实使用、交互走查和阶段退出条件。

## 阶段总览

| 阶段 | 用户结果 | 状态 |
|---|---|---|
| 0. Agent 技术纵切 | SEEK 岗位能进入动态 Agent 并保存结构化结果 | 已完成：技术纵切 |
| 1. 产品基础与交互重设计 | 打开产品就能理解、配置并完成核心任务 | 已完成：作者走查 |
| 2. Career Knowledge Base | 从已有多类资料自动建立可追溯职业知识库 | 已完成：作者真实资料走查 |
| 3. Jobs/Application Workspace | 保存、回看并推进岗位和申请 | 下一阶段，已有后端基础 |
| 4. 材料与申请闭环 | 管理多个岗位版本并完成真实申请准备 | 首个 Source-first 纵切 |
| 5. Job Enrichment 与 Career Intelligence | 补全岗位来源并形成长期改进计划 | 未开始 |
| 6. 可分享产品 | 朋友也能安装、配置、使用和恢复 | 未开始 |
| 7. 最终验证与发布 | 用真实结果评估产品并决定开源/商店发布 | 延后 |

这里的“已完成”表示相应阶段达到 code complete，并由作者完成该阶段用户旅程走查；不表示未参与开发的用户已经独立验证，也不表示 V2 已发布。朋友级安装与首次使用验证属于阶段 6，最终产品评价和发布判断属于阶段 7。

## 阶段 0：Agent 技术纵切

目标：证明现有扩展能够承载真实的 Agent 决策，而不是固定步骤的模型调用。

已完成：SEEK `JobPosting`、本地安全 API、PydanticAI 单 Agent、四个通用能力工具、结构化结果、SQLite、基础材料和自动化纵切。

后续产品阶段继续积累不同岗位和个人资料下的真实输出质量；真实登录 SEEK、真实目标岗位和 Qwen3.7-Plus Key 的首轮 smoke test 已完成。

阶段结论：技术方向成立且首个真实纵切跑通，不等于完整产品已经完成。

## 阶段 1：产品基础与交互重设计

目标：重构信息架构和关键交互，让新用户理解产品、完成设置，并沿一条清晰路径处理当前岗位。

已完成：

- 走查当前 Side Panel，记录入口、层级、状态和文案问题。
- 定义首次使用、日常判断岗位、准备申请、回看记录四条主旅程。
- 明确导航层级、当前岗位主页、setup 状态和渐进式结果展示。
- 形成并实现 [产品体验规范](experience.md)、页面状态表和实施边界。
- 重组 V1 筛选与 V2 求职任务的关系。
- 统一 loading、empty、error、success、disabled 和恢复状态。
- 默认突出结论、关键依据和下一步；tool trace 移入详情/诊断。
- 缺少决策事实时直接向用户提问；回答后继续同一岗位分析，而不是留下不可操作的问题清单。
- 回答默认只属于当前岗位运行，不静默写成 Career Library 的跨岗位事实；原分析和继续分析均可追溯。
- 分析中展示来自真实工具事件的检查进度，不展示或伪造模型隐藏思维。
- 建立一致的视觉层级、间距、排版、控件、键盘和响应式行为。
- 保持现有 React 页面边界，不为视觉改版引入新框架或组件库。

阶段结论：作者已在真实 SEEK 和 Qwen 上完成提取、分析、失败恢复、实时工具进度、追问/继续与主要操作走查，发现的关键交互问题已修正。本阶段关闭。

退出条件：

- 在无既有配置的首次使用场景中，不阅读 README 也能从产品内理解用途、系统状态和首个动作。
- 用户能从当前 SEEK 岗位完成“读取 → 分析 → 理解 → 采取行动”。
- Agent 要求补充事实时，用户能在当前页面回答并继续，不被卡在只读结果中。
- Agent 服务/资料未配置时有明确引导，不出现无从下手的空页面。
- V1 筛选仍容易找到且无功能回归。
- 作者进行至少一次完整走查，主要困惑已修正。

本阶段不增加新网站、RAG、多 Agent、完整 evaluation 或大批新工具。

## 阶段 2：Career Knowledge Base

目标：用户添加已有多份 CV、Visa、证书和项目文档后，Kiwi 自动建立可追溯的职业知识库；用户只处理真正需要判断的异常，不重新填写已有资料。

CV 解析、原件保存和 Agent 原文搜索是可复用技术基础；真实使用已经证明“固定 Profile 表单为主、CV 导入为辅”的产品模型不成立，旧双轨已删除。

Source、FTS5 chunks、Source-bound Claims、冲突确认、Source-native UI、Agent 自主 Claims/chunks/original 检索与 v8 单轨迁移已经完成。作者已真实走查两份不同用途 CV、Visa、课表、独立项目 Markdown、敏感资料下钻、追问/续跑、恢复和首个材料链路，本阶段关闭。

基础 CV 选择、岗位 variant、版本和 FlowCV 式编辑属于阶段 4；GitHub/local folder/ZIP、语义索引和 parent-section 只有出现真实需求时再进入后续资料库扩展，均不再阻塞 Stage 2。

## 阶段 3：Jobs/Application Workspace

目标：把一次分析结果变成可保存、回看、比较和推进的岗位与申请空间，并为后续多个材料版本提供稳定归属。

范围：

- 新建全页面工作区；Side Panel 继续只服务当前 SEEK 岗位。
- 列出已分析岗位，显示岗位身份、Recommendation、截止日期、更新时间、是否已有材料和是否已申请。
- 重新打开保存的分析、关键证据、下一步和材料；同一岗位重分析保持清楚的历史关系。
- Recommendation 继续使用 Agent 的 `APPLY / MAYBE / SKIP`；分析、材料和申请进展从已存在事实得出，只有实际提交需要用户标记 `Applied`，不建立额外人工状态队列。
- 支持用户补充或修正缺失的截止日期，不把猜测保存为事实。
- 从当前岗位进入工作区，并从工作区返回原岗位或申请入口。

详细增量和数据边界见 [Stage 3 实施计划](stage-3-job-application-workspace-plan.md)。任意公司详情页读取和公司官网来源补全移到阶段 5，不阻塞工作区与材料闭环。

退出条件：

- 用户能在离开当前 SEEK 页面后找到此前岗位，并回答“Agent 怎么建议、已经准备了什么、是否已申请、下一步是什么、何时行动”。
- 同一岗位的分析、材料和 applied 事实只有一个清楚归属，重新分析不会产生重复岗位。
- 截止日期缺失时明确显示未知并允许修正；已知日期可用于排序。
- 至少以三个真实岗位走查列表、详情、状态、重开和材料恢复。

## 阶段 4：材料与申请闭环

目标：解决单一 CV 工具的限制，让用户安全、快速维护多个岗位版本。

当前实现：`Prepare application` 已接通首条 Source-first 纵切。材料 Agent 使用已完成分析、Source-bound Claims、分析检索片段和岗位回答，选择可追溯来源并生成摘要、强调项、章节顺序和 Cover Letter；确定性渲染器保留基础 CV 的已抽取记录。CV 与 Cover Letter 按 Analysis action 独立生成，不因其中一项不适用而隐藏另一项。材料 snapshot 与内部 `preparing` 状态自动保存；Side Panel 只显示摘要与 `Mark applied`，完整 CV、Cover Letter 临时编辑和下载在可刷新恢复的独立扩展页面中完成。

这仍不是本阶段完成：基础 CV 暂按岗位用途/最近上传自动选择，页面编辑不会写回版本，也还没有跨岗位材料历史列表；多 variant、差异审批和可靠 PDF 分页均未实现。

范围：

- Career Library 来源记录、一个或多个基础 CV、独立岗位 variants。
- Agent 提议选择、排序、删减和谨慎措辞调整；显示差异与 evidence 来源。
- 用户逐项接受、拒绝、编辑并批准。
- 岗位针对性的 Cover Letter 编辑与版本保存。
- 一个稳定 ATS-friendly 模板、打印/PDF 导出和材料 snapshot。
- FlowCV 式结构化 CV 工作台：实时预览、章节排序与显隐、多个基础 CV 和独立岗位版本；不以自由画布或主题市场为前置目标。
- 材料、岗位、申请状态和关键日期关联。

退出条件：

- 用户能为真实岗位产出一套自己愿意提交的材料。
- 多个岗位版本独立存在，Library 来源和基础 CV 不受隐式改写。
- unsupported claim 被阻止或明确标记。
- 关闭并重开产品后可继续编辑和追踪。

## 阶段 5：Job Enrichment 与 Career Intelligence

目标：补全单一招聘网站缺失的信息，并把多次求职中分散的信息转成长期可执行反馈。

范围：

- 用户在任意公司招聘岗位详情页主动选择“读取当前岗位”，检查结构化预览后确认保存；不识别全站列表或注入筛选按钮。
- SEEK 信息不足时按需查找公司官网原始岗位，比较申请入口并保存来源与时间。
- 聚合高频硬要求、技能、工具、经验和 work-right 限制。
- 结合截止日期、已有基础和投入时间分类为立即可补、下次申请前可补、长期建设。
- 生成可跟踪的学习/evidence backlog。
- 基于公开资料给出 GitHub 项目、README、demo、测试和 LinkedIn 内容改进建议。
- 完成成果可作为新 Source 加入 Career Library。

退出条件：

- 至少用两个结构不同的公司岗位页验证手动读取、预览确认、来源比较和失败恢复。
- 每条建议能追溯到岗位要求或个人资料缺口。
- 用户能接受、排期、完成或拒绝建议。
- 结果不是重复的通用职业建议。

## 阶段 6：可分享产品

目标：让未参与开发的朋友可以安全使用。

范围：

- 当前本机服务的安装、启动、健康检查、升级和数据迁移；若此前真实使用证明需要其他交付方式，再单独评估。
- 模型 Key/Provider 配置、费用提示和失败恢复。
- 示例资料、产品内帮助、隐私、备份、删除和诊断。
- 可访问性、兼容性、性能和真实设备回归。

退出条件：

- 一名新用户仅依据产品引导完成安装、建档和首个岗位分析。
- 常见服务、Key、网络和数据错误都有可理解的恢复动作。
- 私人数据不会出现在仓库、普通日志或错误报告中。

## 阶段 7：最终验证与发布

目标：产品主要能力完成后，用真实结果判断质量和下一步，而不是为了展示反向设计产品。

范围：

- 真实使用记录、人工材料审核和必要的离线案例评估。
- 决策正确性、事实一致性、unsupported claim、耗时和费用复盘。
- 根据最终产品状态更新开源 README、安装文档、案例和 Stage 2 作品集快照。
- 评估 Chrome Web Store 合规、隐私披露和维护成本后再决定是否发布。

退出条件：

- 对外能力和结果都有可复现证据。
- 已知限制、隐私、费用和适用范围清楚。
- 发布与否是产品决策，不是证明项目成功的必要条件。

## 持续规则

- 每次改动运行相称的 typecheck、lint、单元或端到端测试。
- 安全、数据完整性、evidence 校验以及材料定稿和最终提交的用户确认不能延期。
- 当前阶段没有退出前，新想法先记录到对应后续阶段。
- 不按“AI 两天完成了原两周代码量”跳过产品走查和真实验证。
