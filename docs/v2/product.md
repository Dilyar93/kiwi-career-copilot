# V2 产品定义

## 1. 产品愿景

让个人求职从“散落的岗位、简历文件、Cover Letter、申请记录和改进建议”变成一个连续、可信、可执行的本地工作空间。

产品不是简单给 JD 打分，也不是自动海投工具。它应持续理解用户已经确认的背景和 evidence，在不同岗位中采取不同动作，并把每次申请产生的信息积累回个人求职系统。

## 2. 当前目标用户

首要用户是项目作者本人：刚到新西兰的国际学生，需要同时处理 work rights、课程时间、地点、当地招聘习惯、个人资料建设和多个岗位版本的材料。

第二层用户是有相似需求、愿意在本机配置模型 Key 的朋友。只有首要用户的真实流程稳定后，才进入可分享产品阶段。

## 3. 核心问题

### 3.1 找到值得投入的岗位

SEEK 能表达“想找什么”，但负向排除能力有限，岗位详情还可能缺少截止日期、完整要求或公司官网来源。用户需要快速判断硬条件、地点、时间、匹配项和信息缺口。

### 3.2 从已有资料建立可信的职业知识库

CV、项目经历、签证、课表、技能、GitHub 和申请历史分散在不同文件中。用户不应为了使用 Agent 再手工重建这些资料；产品需要保存来源、自动理解常用事实，并让所有结论能够回到原文。

### 3.3 为不同岗位高效准备不同材料

单一 CV 工具难以管理大量轻微不同的岗位版本。用户需要从 Master Data 生成独立 variant，清楚看到改了什么、依据什么，并继续人工编辑。

### 3.4 从求职过程获得长期反馈

单个岗位的 gap 没有积累价值。产品应逐步聚合高频硬要求、短期可补能力和长期建设方向，并转化为 GitHub、LinkedIn、学习和 evidence 计划。

## 4. 产品原则

### Product-first

- 首次打开要解释用途、当前状态和下一步。
- 按用户任务组织产品，不按数据库表、工具名或技术模块堆入口。
- 正常使用不要求编辑 JSON、运行 CLI 或理解 Agent trace。
- UI/交互、错误恢复、隐私提示和可访问性是核心功能。

### Agent-first

- Agent 根据岗位、资料库目录、历史和 observation 决定需要什么信息、搜索什么、下钻到哪一层、是否提问以及最终建议；不同岗位可以不调用工具，也可以走不同路径。
- 确定性代码只执行检索/存储能力并守住 authentication、privacy、provenance、schema、数据完整性和恢复边界，不替 Agent 写岗位语义 `if/else`、固定工具顺序或自动补问题。
- Claims、chunks 和 original 是 Agent 可自主选择的三层读取能力，不是系统预先编排的 workflow。
- 验收案例只用于验证结果和边界，不得反向写成“这个岗位必须问这个问题”的生产分支。

### Evidence-grounded

- 原始来源是最终可回查依据，结构化 Claim 是带精确引用的派生查询层。
- source-backed 事实可以用于有引用的分析；高风险事实、来源冲突和来源中不存在的对外新声明必须由用户确认。
- 缺少证据时输出 unknown 或 gap；检索不到不能推断用户不具备某项能力。
- Agent 提议的改写必须可追溯、可比较、可拒绝。

### Local-first 与用户控制

- 私人资料、历史和材料默认留在本机。
- 本地保存完整原件；上传理解会在明确披露后把提取文本发送给模型 Provider，后续岗位任务先发送最小事实或片段，必要时由 Agent 逐层深入读取。
- 用户可以查看、修改、导出和删除数据。
- 敏感声明、材料定稿、表单填写和最终提交必须由用户确认。

### 渐进扩展

- 当前只承诺 SEEK。
- 新网站通过 adapter 接入，但只在存在真实需求和可验证样本时实现。
- 资料库采用结构化 Claim 与可回溯原文检索；全文、语义或分层检索按真实资料规模逐步增强。
- 先支持一个稳定模型 Provider；多 Provider 是可用性需求，不是架构展示目标。

## 5. 核心用户旅程

### 5.1 首次使用

```text
理解产品与隐私边界
→ 检查本地服务和模型配置
→ 添加已有 CV、项目或其他职业资料
→ Kiwi 自动理解并只要求处理冲突、高风险或低置信度内容
→ 在 SEEK 打开第一个岗位
```

成功标准：用户无需阅读开发文档或运行数据导入命令，也知道还缺什么以及如何继续。

### 5.2 日常发现和判断岗位

```text
浏览经过 V1 规则过滤的 SEEK 职位
→ 打开当前岗位
→ Agent 读取岗位与必要的个人上下文
→ Agent 按需检索 Claims、原文片段、指定原件、申请历史或外部来源
→ 给出申请、待确认、稍后或跳过建议
→ 解释关键依据和下一步
```

成功标准：用户能回答“为什么值得投、什么会阻止我、缺什么信息、现在该做什么”。

### 5.3 准备申请材料

```text
选择准备申请
→ 从 Master Data 建立岗位 variant
→ 查看 CV Change Plan 和 evidence 来源
→ 接受、拒绝或编辑改动
→ 生成并编辑 Cover Letter
→ 导出材料并记录申请状态
```

成功标准：不同岗位的材料彼此独立，Master Data 不被污染，用户愿意提交最终结果。

### 5.4 回顾和提升

```text
积累岗位、gap、申请和结果
→ 识别高频要求和重复缺口
→ 结合截止日期与投入时间分类
→ 生成短期补强和长期建设计划
→ 将完成成果转回 evidence
```

成功标准：建议能追溯到真实岗位需求，不是通用鸡汤，并可被跟踪和关闭。

## 6. 产品能力地图

| 能力域 | 目标能力 | 当前成熟度 |
|---|---|---|
| SEEK 浏览增强 | 负向规则、状态和距离筛选 | 可用的 V1 能力 |
| Career Knowledge Base | Sources、Chunks、Claims、Review items 和来源下钻 | Source-only 纵切已实现并经过两份 CV、Visa 与课表真实走查；项目 Markdown 待最后 smoke test |
| Job workspace | 提取、分析、截止日期、行动建议和长期回看 | 当前岗位分析已可用；全页面岗位工作区是下一阶段 |
| Material workspace | Master CV、variants、差异编辑、Cover Letter、导出 | Source-first 生成、snapshot 和全页面预览原型 |
| Application tracking | 状态、历史、材料和岗位关联 | SQLite/API 基础已实现，尚无用户工作区 |
| Career intelligence | 高频要求、gap、学习/GitHub/LinkedIn backlog | 未实现 |
| Shareable local product | onboarding、安装、配置、迁移、恢复 | 未实现 |

详细事实以 [当前状态](current-state.md) 为准。

## 7. 主要产品界面目标

最终信息架构应围绕用户任务，至少区分：

- **Today / Current Job**：当前岗位、结论、关键证据和下一步。
- **Jobs**：保存的岗位、状态、截止日期和回看入口。
- **Applications / Materials**：申请记录、CV variants、Cover Letters 和导出。
- **Library / 资料库**：来源、自动理解的事实、待确认问题和 CV variants。
- **Career**：跨岗位洞察和改进计划。
- **Settings / Diagnostics**：Provider、本地服务、隐私、数据和技术诊断。

这只是产品层级要求，不是已确认的 UI 稿。正式重设计时应基于当前 Side Panel 尺寸、真实任务和用户走查另写 UI 方案。

## 8. 当前不做

- 自动提交申请或无人值守海投。
- 未经确认自动填写敏感、法律或医疗声明。
- 修复 Trade Me。
- 同时建设多个模型 Provider、GraphRAG、多 Agent 或分布式任务系统。
- FlowCV 式自由画布、多主题市场或完整排版引擎；阶段 4 仍会实现结构化编辑、实时预览、章节排序与显隐、多份基础 CV 和岗位版本。
- 在产品主流程完成前扩建 evaluation 平台和展示包装。
- 当前阶段投入 Chrome Web Store 合规与重新发布；但安全和隐私要求持续有效。

## 9. 产品成功定义

产品主要阶段完成时，真实用户应能够：

1. 独立完成安装、配置和个人资料建立。
2. 在真实 SEEK 岗位上获得可信且可解释的行动建议。
3. 快速制作、编辑并恢复多个岗位版本的 CV 和 Cover Letter。
4. 管理岗位、申请、截止日期和结果，不依赖外部散乱记录。
5. 从多次求职中得到有证据、有优先级、可跟踪的提升计划。

自动化测试、演示效果或一次模型输出都不能单独证明上述成功。
