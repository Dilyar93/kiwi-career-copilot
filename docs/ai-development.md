# Vibe-coding 文档与开发约定

本文定义 AI 参与产品迭代时如何读取、修改和维护文档。目标是减少上下文冲突，让新会话能够快速恢复真实产品状态。

## 1. 文档不是聊天记录

产品文档只保存未来仍需要知道的事实：

- 产品为谁解决什么问题。
- 当前代码和产品真实做到什么。
- 当前阶段与完成条件。
- 稳定的架构、安全和数据边界。
- 会影响后续工作的设计变化及原因。

临时想法、每日流水账、一次性的提示词、按天计划、过程复盘和面试话术不应长期占据权威文档。

## 2. 两类版本文档

### 已发布版本：冻结快照

V1 这类版本应保留：

- `README.md`：版本定位和文档入口。
- `product.md`：当时真实交付的用户能力与边界。
- `architecture.md`：实际代码架构和维护约束。
- `implementation-review.md`：原设计、实际结果、已知限制和后续处理。

修复对该版本事实的错误可以修改；新产品设想不再写入。

### 当前开发版本：living docs

V2 应持续维护：

- `README.md`：AI 首读入口和权威顺序。
- `product.md`：稳定产品定义与用户旅程。
- `current-state.md`：当前实现、缺口、风险和下一阶段。
- `roadmap.md`：按阶段排列的结果与退出条件。
- `architecture.md`：当前结构和目标边界。
- `decisions.md`：重要设计演变。
- `quality.md`：持续检查和最终评价边界。

不要让两份文档同时承担同一种职责。

## 3. AI 开始任务前

最小读取顺序：

1. 仓库工具自动提供的根 `AGENTS.md`
2. `docs/README.md`
3. `docs/v2/README.md`
4. `docs/v2/current-state.md`
5. 与任务相关的 `product.md`、`roadmap.md`、`architecture.md`、`experience.md` 或 `quality.md`
6. 实际代码、tests 和配置

只有遇到“为什么以前这么写”时才读 `decisions.md`；只有需要核对历史原文时才读 `archive/`。

任何实现计划必须同时引用：用户结果、当前代码事实、所属阶段和退出条件。不能只从旧企划或一段聊天内容开始编码。

阅读顺序用于建立上下文，文档权威顺序用于处理冲突，两者不是同一概念。仓库早期主要是本地修改，Git 历史不能用于还原原始设计或覆盖当前 living docs。

## 4. Agent-native 核心原则

这是不可违反的产品与代码评审规则，不只是一段 prompt：

- Agent 决定哪些事实重要、检索什么、是否查看 Claims/chunks/指定原件、信息是否足够、是否值得提问以及最终建议。
- 普通代码只提供能力并守住信任边界：authentication、持久化、provenance、输入输出 schema、privacy、幂等和恢复。
- 普通代码不得写入岗位语义结论、强迫固定工具顺序、自动制造追问，或把某个验收案例改写成生产 `if/else`。
- 检索代码可以执行并排序 Agent 提出的 query，但不得替 Agent 决定 query 的含义或职业结论。
- 模型不能绕过来源、隐私和数据完整性校验；这些是信任边界，不是 workflow 决策。
- 候选人知识只能有一条权威路径。新架构取代旧架构时应删除旧运行路径；没有真实已发布数据迁移需要时，不得以“兼容”为由保留隐形 Profile/Evidence 双轨。

向 Agent 代码增加确定性分支前，必须先问：“它是在保护信任边界，还是在替 Agent 做语义判断？”后者应改为向 Agent 提供能力和上下文。测试验证工具选择自由与安全边界，不要求唯一推理轨迹。

## 5. 完成任务后更新什么

| 变化 | 应更新 | 不应更新 |
|---|---|---|
| 实现/删除了能力 | `current-state.md` | 不重写整个 product vision |
| 用户目标或产品边界改变 | `product.md`，必要时 `decisions.md` | 不只留在聊天中 |
| 阶段完成或顺序改变 | `roadmap.md`、`current-state.md` | 不创建第二份路线图 |
| 架构/数据/安全边界改变 | `architecture.md`，重要变化加 `decisions.md` | 不把计划写成已实现 |
| 测试命令或质量政策改变 | `quality.md` | 不在多份文档复制固定测试数量 |
| 纯 bug 修复或内部重构 | 通常不改产品文档 | 不写流水账 |

README 只在入口、定位或公共使用说明变化时更新。

## 6. “完成”的三个层级

AI 报告状态时必须区分：

1. **Code complete**：实现存在，自动化检查通过。
2. **Product complete**：正常用户能从 UI 完成旅程，状态和错误可理解。
3. **Validated**：在真实数据、真实环境或目标用户中证明有价值且可靠。

前一层不能自动代表后一层。`current-state.md` 应明确写出属于哪一层。

## 7. 阶段计划的生命周期

- 路线图只保留阶段目标，不写 Day 1–10 或估算工时作为完成标准。
- 即将实施一个复杂阶段时，可以新增一份短期实施计划；它必须有明确结束条件。
- 实施结束后，把长期事实合并进 `current-state.md`、`architecture.md` 或 `decisions.md`。
- 已完成的临时计划应删除或归档，不能继续与当前路线图并列。
- UI 重设计、数据迁移等需要独立评审的工作，应在进入对应阶段时再创建详细文档，不提前空写。

## 8. 旧文档的归档与删除

当前仓库缺少可用的 Git 历史，因此本次重构先保留 raw documents 作为还原来源，并在 `archive/README.md` 明确标为非权威。

当以下条件都满足后，可以从主文档树删除 raw plans：

- 新版产品、架构、状态和 decisions 已经覆盖仍有价值的信息。
- 这些文档已进入可靠 Git 历史或另有备份。
- 当前链接和自动化/人工指令不再引用它们。

对外开源时，通常不需要携带所有 prompt 和过期日计划。保留版本快照、release notes 和重要 decisions 即可；历史细节由 Git 提供。

## 9. 防止文档再次失真

- 用代码、schema、测试和真实使用结果核对事实，不照抄旧 README。
- “已实现”后写清入口和限制；“目标”不得使用完成时态。
- 不复制同一功能清单到多份文档。
- 日期只用于状态快照和发布记录，不用于放大任意开发周期。
- Evaluation、demo、商店材料与产品主文档分开，且只在相应阶段启用。
- 每次新增文档前先判断能否更新现有权威文档；默认不新增。
